# Issue Integration Comparison

This reference lists which capabilities each **issue provider** supports: issue import, status transitions, time tracking/worklog submission, comments, subtasks, attachments, filtering options, auto-import to backlog, story points, due dates, and other provider-specific behavior. Use it to compare providers or to see what to expect when you enable one.

For an overview of how integrations work and how to set them up, see [[4.24-Integrations]] and [[2.07-Manage-Task-Integrations]]. For a comparison of **sync** providers (WebDAV, Dropbox, SuperSync, local file), see [[3.08-Sync-Integration-Comparison]].

## Core Capabilities (All Providers)

Every issue provider supports the same basic operations: checking that the integration is enabled, testing the connection, opening the issue in the external system, fetching an issue by ID, searching issues, and adding an issue as a task in the app. All providers also support refreshing already-imported tasks so that changes in the external system (title, status, etc.) are reflected locally. Each provider has a configurable **poll interval** (or none) for how often the app checks for updates. Beyond that, support for status transitions, worklogs, comments, subtasks, attachments, and filtering depends on the provider and the external API.

## Feature Matrix Summary

| Provider        | Import | Status        | Worklog    | Comments | Subtasks | Attachments | Filtering            | Auto-import | Story pts | Due dates |
| --------------- | ------ | ------------- | ---------- | -------- | -------- | ----------- | -------------------- | ----------- | --------- | --------- |
| Plainspace      | Yes    | Two-way       | No         | No       | No       | No          | Space                | Yes         | —         | Yes       |

**Legend:** **Status** = configurable or automatic status transitions; **Worklog** = time tracking submission to the external system ("On done" = dialog when a task is completed); **Auto-import** = automatic import of new issues into backlog.

## Per-Provider Details

### Plainspace

Plainspace is Super Productivity's own **collaboration** layer (a shared workspace at [plainspace.org](https://plainspace.org)), so it behaves differently from the read-mostly issue trackers above. You connect a **Space** with a personal API token (`pat_…`), and the tasks **assigned to you** in that Space import into the bound project.

- **Issue import:** Tasks assigned to you in the connected Space. A **claim pool** in the work view also lists **unclaimed** tasks you can claim into your list.
- **Status transitions:** **Two-way done sync** — completing a task locally marks it done in Plainspace, and a task completed in Plainspace is marked done on the next poll.
- **Title & schedule:** **Pull only** — a rename or reschedule made in Plainspace pulls in on the next poll (`scheduledAt` → `dueWithTime`), but renaming or rescheduling the task locally is **not** pushed back. **Recurring** tasks are flagged in the claim pool and task panel; the Plainspace server advances the schedule to the next occurrence.
- **Recurring tasks:** A recurring Plainspace task stays **one** local task across all its occurrences — Plainspace keeps a single item and moves its schedule forward. Once the server has advanced to the next occurrence, the local task is reopened and rescheduled on the next poll; if you archived it in the meantime, it is restored from the archive as the next occurrence. Consequences worth knowing: notes and subtasks carry over, **completed subtasks stay completed** (only the parent reopens), **tracked time accumulates across all occurrences** rather than starting fresh (unlike Super Productivity's own repeating tasks), and the completed occurrence leaves no separate archive entry. Archiving does not stop a recurring task from coming back, and neither does deleting it (it is re-imported on the next poll) — end or unassign the repetition in Plainspace instead. For the same reason, avoid setting a **time estimate** on a recurring Plainspace task: it is compared against the accumulated total, so once the accumulated time reaches the estimate, a task without subtasks counts as zero remaining time in the schedule on later occurrences. Per-day tracking (worklog, daily summary, time exports) stays correct either way.
- **Worklog / Comments / Subtasks / Attachments:** Not supported.
- **Filtering:** By Space (one provider instance per Space).
- **Auto-import:** Assigned tasks auto-import into the bound project's backlog; the poll interval is 5 minutes. A task that **leaves** your Plainspace list (unassigned or removed) is automatically removed locally.
- **Sharing a project:** You can turn an existing local project into a shared Space from the **project context menu → Collaborate on Plainspace**, or via the **Collaborate on this project** toggle when creating a project. This provisions a Space and a bound Plainspace provider in one step. See [[2.07-Manage-Task-Integrations]].
- **Disconnecting the account:** On an unlinked project, open **Collaborate on Plainspace → Disconnect account** in the space picker. This removes the saved account from this device and closes the dialog. Opening collaboration again, including after restarting Super Productivity, asks you to connect again. Existing project integrations retain their own credentials and keep syncing; to stop them, open each relevant Plainspace integration in the **issue provider panel**, then choose its **gear icon → Delete**. Disconnecting does not revoke the API token or sign you out of the Plainspace website. Editing or deleting a provider, or restoring a backup, does not clear the separate saved account.

## Implementation Notes

- **Worklog submission:** None of the listed providers posts time entries back.
- **Subtask support:** None of the listed providers imports subtasks.
- **Auto-import and polling:** Providers poll for updates on an interval and can auto-import new issues into the backlog; exact behavior is provider-specific.
- **Collaboration vs. import:** Plainspace is collaboration-oriented — done state syncs both ways, title and schedule pull in from Plainspace, and you can share a local project as a shared Space. Other providers are primarily imports from external trackers.

Optional capabilities (e.g. subtasks, attachments, sending updates back to the external system) are implemented per provider depending on what the external API supports.
